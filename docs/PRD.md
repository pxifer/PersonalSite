# 个人网站产品需求文档（PRD）

版本：v1.0  
更新日期：2026-10-15  
用途：指导第一版个人网站的内容准备、UI/UX 设计、开发与验收。

## 1. 网站定位与目标

网站是面向招聘方与潜在合作方的全栈 / 软件工程师个人品牌站，以代表项目展示能力，以技术文章体现思考与持续学习。中文为主，保留技术术语和项目名的英文原文。

核心表达：能够理解需求，并将其转化为完整、可靠的产品。通过真实职责、工程决策和可验证成果支撑这一定位。

### 1.1 目标访客与核心路径

| 访客     | 主要需求                       | 网站应提供的答案                                 |
| -------- | ------------------------------ | ------------------------------------------------ |
| 招聘方   | 快速判断能力与岗位匹配程度     | 专业方向、代表项目、个人职责、精选经历、联系方式 |
| 合作方   | 判断是否具备完成合作项目的能力 | 擅长解决的问题、项目实现与成果、合作联系入口     |
| 技术同行 | 阅读实践经验，了解技术思路     | 技术文章、清晰的分类标签、项目源码入口           |

首要访问路径：首页 → 代表项目 → 项目详情 → 联系。次要路径：博客列表 → 搜索或筛选 → 文章阅读 → 关于作者或联系。

成功标准：首次访问者无需滚动即可识别姓名、专业方向与主要行动；浏览首页和一个项目详情后，能够说明作者的能力、项目贡献，并找到联系入口。第一版通过人工走查验证，不接入访问统计。

### 1.2 第一版范围

- 首发 1–2 个核心项目、3–6 篇文章，以及个人介绍、技能、精选经历和联系方式。
- 首页负责叙事，项目和文章拥有独立列表及详情页，关于页提供完整个人信息。
- 使用本地 Markdown / MDX 文章文件和结构化项目资料维护内容；不要求公共 API、数据库或内容后台。
- 不做账号、评论、点赞、联系表单、PDF 简历、RSS、访问统计、全文搜索、双语切换、整站浅色主题、Now 模块或开发活动流。
- 不加入粒子星图、快捷指令面板、滚动劫持等特殊交互。

## 2. 页面结构与全站规则

| 页面       | 路径约定           | 主要内容                                   |
| ---------- | ------------------ | ------------------------------------------ |
| 首页       | `/`                | 定位、精选项目、技能、经历、文章、联系     |
| 项目列表   | `/projects`        | 1–2 个精选项目，后续允许扩充               |
| 项目详情   | `/projects/{slug}` | 精简项目说明、成果、封面或截图、外部链接   |
| 博客列表   | `/blog`            | 文章列表、搜索、分类和标签筛选             |
| 文章详情   | `/blog/{slug}`     | 文章元信息、正文、目录、返回入口           |
| 关于       | `/about`           | 个人介绍、能力与工具、经历里程碑、联系方式 |
| 未找到页面 | 无效路径           | 清晰提示，返回首页或博客的入口             |

### 2.1 导航与联系入口

- 页头使用姓名字标或首字母，点击返回首页。主导航为“首页 / 项目 / 博客 / 关于”，高亮当前栏目，详情页归属于对应栏目。
- 页头置顶，背景保持文字可读；锚点跳转应预留页头高度，不能遮住标题。
- 桌面端导航右侧放置“联系我”。首页中点击滚动到 `/#contact`；其他页面跳转到 `/about#contact`。关于页也展示完整联系信息。
- 移动端使用菜单按钮，菜单包含主导航及联系入口；支持打开、关闭、Esc 关闭和选择链接后关闭，并将关闭后的焦点还给菜单按钮。
- 页脚保持简洁：姓名、年份、GitHub 与邮箱入口。不使用未经确认的社交账号或备案信息。

### 2.2 通用交互

- 普通站内链接在当前标签页打开；GitHub、演示及其他外部链接在新标签页打开，并提供可识别的外链提示。
- 点击邮箱可调用邮件应用，另设“复制邮箱”按钮。复制成功显示“邮箱已复制”；失败时显示完整邮箱和手动复制提示。
- 未提供的外部链接直接隐藏，不使用 `#`、假地址或无法点击的占位按钮。
- 卡片主标题和主要内容区进入详情，独立外链单独可点击；避免把链接嵌套在链接内。
- 内容不存在时显示适当空状态；未知项目或文章地址进入未找到页面，不生成空详情。

## 3. 各页面内容与交互

### 3.1 首页

首页依次呈现以下模块，各模块承担不同信息任务。

| 模块     | 内容与布局                                                                                                             | 行动入口                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 首屏     | 可联系状态、姓名、全栈 / 软件工程方向、一句个人主张及简短介绍；以大字号文字为主体，渐变微光为背景                      | 主按钮“查看代表项目”滚动至精选项目；次按钮“关于我” |
| 精选项目 | 1–2 个大幅项目展示，包含抽象封面、名称、简短描述、个人职责、主要技术标签和一项真实成果；单项目时占满内容区，不留空卡位 | 项目详情、“全部项目”                               |
| 技能体系 | 按解决问题的能力分组，例如界面与体验、服务与数据、交付与工程质量；列出实际使用的技术和工具，并关联项目证据             | 对应项目或关于页                                   |
| 精选经历 | 2–4 个关键里程碑，每项包含时间、角色或阶段、一句贡献；不足时按实际数量展示                                             | “了解更多经历”进入关于页                           |
| 最新文章 | 按发布日期倒序展示最多 3 篇，包含标题、摘要、日期、主分类                                                              | 文章详情、“全部文章”                               |
| 联系区域 | 简短合作邀请、邮箱复制、GitHub 等已提供的社交链接                                                                      | 发邮件、复制邮箱、外链                             |

首屏状态徽标默认文案为“欢迎交流与合作”，上线前由本人确认并可通过内容配置修改。示例状态不代表已经确认的求职意向，不展示未经确认的“正在求职”或“可立即入职”。

### 3.2 项目列表

- 页首为“项目”标题和一句说明；下方采用精选作品布局，突出 1–2 个项目的完整信息。
- 卡片包含封面、名称、摘要、个人职责、技术标签及详情入口；技术标签优先展示最相关的 3–5 项，完整技术栈见详情。
- 桌面端使用横向图文布局，移动端改为封面在上、文字在下；不因只有一个项目而保留空列。
- 第一版不提供筛选、搜索或分页。内容排序由作者指定，优先展示最能证明当前能力的项目。

### 3.3 项目详情

- 顶部展示返回项目列表、名称、一句话简介、项目时间、个人职责、技术栈，以及存在的 GitHub / 在线演示链接。
- 正文采用精简小节：项目背景、我的工作、关键难点与方案、成果与收获。每节使用短段落或少量要点，避免扩张为长篇案例研究。
- 成果可以是已完成的能力、实际交付或有依据的指标；没有数据时使用定性描述，不编造增长、性能或用户规模。
- 有真实截图时展示图片及简短说明，点击可放大，支持关闭按钮、Esc 和键盘焦点管理。没有截图时省略截图区，保留抽象封面和正文，不呈现空画廊。
- 抽象封面标注“项目视觉封面”；截图只使用对应项目的真实素材，不以生成界面代替实际成果。
- 页尾提供返回项目列表及联系入口。只有一个项目时不展示“下一个项目”。

### 3.4 博客列表

- 标题下提供搜索框、主分类和标签筛选，默认展示全部已发布文章，按发布日期倒序排列。
- 每篇列表项展示标题、简短摘要、发布日期、一个主分类及标签，采用便于扫读的文字列表，不强制文章配图。
- 搜索范围为标题、摘要、分类和标签，不搜索正文或代码。输入后即时更新结果，不要求点击提交；匹配忽略英文大小写及首尾空白。
- 每次可选一个分类和一个标签，均有“全部”或清除选项；搜索、分类与标签共同生效。显示结果数量及“清除筛选”入口。
- 分类与标签仅展示已发布文章实际使用的值；分类保持少量稳定主题，标签用于具体技术或问题，避免同义词重复。
- 无结果时显示“没有找到相关文章，试试其他关键词或清除筛选”；未发布任何文章时显示内容准备中，不显示虚假文章。
- 第一版不分页。文章增长到 10–12 篇以上时重新评估分页需求，不提前实现。

### 3.5 文章详情

- 头部包含返回博客、标题、摘要、发布日期、主分类和标签；存在真实修订日期时显示“更新于”，不自动伪造更新记录。
- 支持 Markdown 常用内容：标题、段落、列表、链接、引用、图片、表格和带语言标识的代码块。MDX 仅在必要时补充轻量内容组件。
- 正文有至少两个二级标题时生成文章目录；桌面端置于侧栏，移动端折叠置于正文之前。点击目录跳转对应标题。
- 代码块支持横向滚动和复制，复制结果有文字反馈；宽表格在局部容器内横向滚动，不能撑宽整页。
- 分类或标签可返回博客列表并应用对应筛选。
- 页尾提供作者简介、关于页、联系和返回博客入口，不显示评论、点赞或阅读量。
- 阅读模式指文章页面的视觉处理：使用安静的深色正文表面、稳定的文字对比和舒适行距，不是独立主题开关。正文背后不播放渐变动画。

### 3.6 关于页

- 展示姓名、专业方向、个人介绍和做事方式，可补充少量与专业形象有关的个人兴趣。
- 技能与工具按能力分类，说明实际用途；不使用“掌握 95%”等熟练度进度条。
- 精选经历以时间倒序里程碑展示，包含时间范围、机构或阶段、角色、贡献。工作、教育、自主项目按真实资料选用，不补写不存在的履历。
- 联系区域展示完整邮箱及有效社交链接，与首页保持同源内容。
- 提供基本打印样式：隐藏导航和装饰、采用深色文字与浅色纸面、保持经历可读；不提供 PDF 下载按钮或专门的简历生成流程。

## 4. 整体视觉与 UI 规范

### 4.1 风格与配色

视觉关键词：未来科技感、专业、克制、清晰。个性来自姓名标识、个人主张、项目选择和内容表达。

| 用途           | 初始设计参考                    | 使用要求                                     |
| -------------- | ------------------------------- | -------------------------------------------- |
| 页面背景       | 深蓝 `#0B1020`                  | 全站基底，避免纯黑大面积压迫感               |
| 卡片与阅读表面 | `#121A2E`                       | 与背景形成轻微层次，文章区域保持纯净         |
| 主要文字       | `#F1F5FF`                       | 标题和正文主要信息                           |
| 次要文字       | `#B6C2DA`                       | 摘要、日期与辅助说明，不使用过暗灰字         |
| 高亮色         | 紫色 `#A78BFA`                  | 链接、焦点和主要交互强调                     |
| 渐变           | 蓝紫 `#6366F1` → 紫色 `#A855F7` | 仅用于首屏氛围、少量重点文字、封面与悬停细节 |

以上为初始视觉基准，实际组合需检查对比度。正文不使用渐变文字；按钮使用能保证标签可读的实色底或已验证的渐变组合。状态不能仅靠颜色表达。

### 4.2 排版与布局

- 采用现代无衬线中文字体栈，如系统字体及可用的苹方、微软雅黑、思源黑体；技术信息局部使用等宽字体，不强制加载大体积外部字体。
- 桌面首屏标题参考 56–72 px，移动端 36–44 px；正文 16–18 px，文章正文优先 18 px、约 1.8 倍行距。
- 页面内容最大宽度约 1160 px，长文正文宽度约 720–760 px。采用统一间距尺度和充足段落留白。
- 首页精选项目比技能和文章模块拥有更强视觉权重；不同内容采用不同布局，避免全页重复相同卡片。
- 卡片使用细边框、适量圆角和轻微层次，发光边缘只在少量交互状态出现。
- 字标必须在小尺寸下可辨识；缺少头像时直接使用姓名或首字母，不生成虚构人物照片。

### 4.3 动效

- 按钮、链接和卡片反馈时长参考 150–250 ms；滚动显现参考 300–450 ms，以淡入和不超过 16 px 的位移为主。
- 内容显现最多执行一次；内容默认可读，动画失效或脚本异常不应使正文永久隐藏。
- 首屏允许低强度渐变漂移，首轮播放不超过 5 秒后停止，不在正文背后持续运动。
- 页面切换只使用短暂淡入，不阻塞导航或阅读；不使用滚动劫持和大幅视差。
- 尊重系统“减少动态效果”设置，关闭氛围动画、滚动位移和过渡；键盘焦点拥有与悬停同等清晰的反馈。

## 5. 响应式与基础质量

| 尺寸              | 布局要求                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------- |
| 手机，低于 768 px | 单列布局，左右留白约 20 px，折叠菜单，项目图片在上；首屏按钮可换行，标签自然折行，减少模糊层并关闭背景漂移动画 |
| 平板，768–1023 px | 保持文字可读，按空间采用一至两列；页头继续使用紧凑菜单，文章目录折叠展示                                       |
| 桌面，1024 px 起  | 完整导航，宽幅项目图文布局，文章在有目录时使用正文与侧栏；超宽屏保持内容最大宽度                               |

- 在 320 px 起的窄屏、常见手机及桌面宽度检查，无整页横向溢出；200% 缩放时核心内容及操作仍可使用。
- 按钮和菜单触控区域至少约 44 × 44 px；所有功能不依赖悬停，移动端可直接操作。
- 页面设置中文语言、清晰标题层级、语义化区域和跳至正文入口；图标按钮有可理解的名称，表单控件有标签。
- 正文与背景对比度至少 4.5:1，大字至少 3:1；键盘焦点可见，复制和搜索结果变化提供适合辅助技术的状态提示。
- 真实截图提供描述内容的替代文字；纯装饰封面图形对辅助技术隐藏，项目名称仍由文本承载。
- 图片预留尺寸避免布局跳动，非首屏图片延迟加载；按显示尺寸提供压缩资源。无需引入三维渲染、持续绘制或大型动画库。
- 支持主流现代 Chrome、Edge、Safari、Firefox；发布前走查桌面浏览器及手机视口，并记录无法验证的平台。

## 6. 内容模型与示例

### 6.1 最小内容字段

| 内容类型 | 必需内容                                                                                  | 可选内容                         |
| -------- | ----------------------------------------------------------------------------------------- | -------------------------------- |
| 个人资料 | 展示姓名、字标文字、专业方向、定位语、简介、已确认的可联系状态、邮箱                      | GitHub、其他社交链接、个人兴趣   |
| 技能分组 | 分组名、解决的问题、真实使用的技术或工具                                                  | 对应项目链接                     |
| 经历     | 时间范围、机构或阶段、角色、简短贡献                                                      | 进一步说明                       |
| 项目     | 唯一稳定 slug、名称、摘要、项目时间、个人职责、背景、难点与方案、成果、技术栈、封面、排序 | 真实截图及说明、GitHub、演示链接 |
| 文章     | 唯一稳定 slug、标题、摘要、发布日期、单一分类、标签、正文、是否发布                       | 真实更新日期、正文图片           |
| 社交链接 | 平台名、真实 URL                                                                          | 简短说明                         |

slug 使用稳定的可读英文短名称；发布后避免随意改变地址。未发布文章不出现在列表、搜索及站点地图中，也不通过直接地址公开。

### 6.2 文案示例（均非真实个人资料）

以下仅说明内容结构和文字语气。示例必须保留标记，开发预览中的示例内容也需标注；公开发布前替换或移除。不得将示例视为已证实的经历、能力或成果。

> **首屏示例**  
> `[展示姓名·待替换]` · 全栈 / 软件工程

> 状态：欢迎交流与合作 `[本人确认后使用]`

> **项目摘要示例**

> 邮箱：`[真实邮箱·待替换]`

### 6.3 发布前内容清单

- 替换姓名、字标、简介、状态、邮箱和全部社交链接；网站域名由部署阶段确认。
- 准备 1–2 个项目的完整最小字段与抽象封面，确认职责和成果真实；截图不作为首发必需条件。
- 准备 3–6 篇真实文章，统一分类和标签命名，检查代码与图片；不把示例标题视为已发布内容。
- 填写实际技能和精选经历；内容不足时精简模块，不通过复制示例填满版面。
- 检查所有示例标记、待替换内容、失效链接和敏感资料；公开页面不得遗留未说明的示例事实。

## 7. 基础 SEO 与分享

- 每个页面使用独立标题和描述。详情页标题包含项目或文章名称及个人姓名，首页突出专业方向。
- 项目和文章具备可直接访问的稳定链接，主要正文可被搜索引擎读取。
- 提供 canonical、站点地图和合理的 robots 设置；正式域名确定后再生成对应绝对地址。
- 设置分享标题、摘要及分享图；无专属图片时使用姓名字标、标题和品牌背景构成的默认分享卡片，不冒充项目截图。
- 未发布内容及未找到页面不进入站点地图；未找到页面返回正确的未找到状态。
- 不引入 RSS、追踪脚本或访问统计。

## 8. 验收场景

| 场景           | 通过标准                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------- |
| 首次浏览       | 首屏可识别姓名、方向、状态与项目入口；首页叙事顺序完整，重点落在核心项目                     |
| 单项目展示     | 只有一个项目时布局完整，无空卡片、无无效的下一项目入口                                       |
| 项目详情       | 能读懂背景、本人职责、难点方案和成果；无截图时无空画廊；缺失外链不显示                       |
| 博客搜索       | 中文关键词及大小写不同的英文可匹配指定字段；分类、标签和关键词共同筛选；清除后恢复全部文章   |
| 搜索空状态     | 无匹配结果时有说明和清除入口，输入或筛选变化后结果正常恢复                                   |
| 文章阅读       | 正文、代码、表格和图片可读；目录按条件出现且定位准确；代码复制有成功或失败反馈               |
| 联系           | 所有页面均能到达联系区域；邮箱复制成功可感知，失败可手动复制；邮件及社交链接指向真实地址     |
| 手机与缩放     | 在 320、390、768、1280、1440 px 视口及 200% 缩放下检查；无整页横向溢出，菜单、筛选和按钮可用 |
| 键盘与动态设置 | 仅用键盘可访问导航、筛选、复制和弹层；焦点清晰，Esc 可关闭相应菜单或弹层；减少动态设置生效   |
| 内容真实性     | 公共页面无未替换的示例身份、假成果或假链接；抽象封面与真实截图区分明确                       |
| SEO 与边界     | 每页标题、描述、分享信息正确；站点地图无草稿；未知文章和项目地址显示未找到页面               |

验收以真实浏览、内容检查和必要的交互检查为主。第一版不需要为流量或转化率搭建额外监控系统。

## 9. 后续可扩展功能

下列内容均不进入第一版，仅在出现实际需要时单独评估：

- 项目数量增长后增加项目分类或筛选；文章超过约 10–12 篇后评估分页。
- 内容积累较多后评估全文搜索和 RSS。
- 存在明确海外受众后增加英文内容与语言切换。
- 招聘材料需要离线分发时增加 PDF 简历。
- 有访问分析需求时评估隐私友好统计；写作流程出现维护负担时评估内容后台。
- 持续收到阅读偏好反馈后评估浅色主题；有明确互动需求时再评估评论及其维护成本。

后续扩展应保留稳定文章和项目链接，并延续现有品牌、移动端体验及无障碍要求。
