# 个人网站技术设计文档

版本：v1.1
日期：2026-10-15  
产品依据：[PRD.md](./PRD.md)  
状态：技术方案已确认；用户指定 GitHub Pages 作为第一版部署平台。

## 1. 技术方案概述

采用 Astro + TypeScript 构建静态个人网站。构建时读取仓库中的个人资料、项目和文章，完成校验并生成 HTML、静态资源、站点地图与搜索所需的文章元信息；浏览器执行搜索、菜单、复制和图片放大等局部交互。

主要受众为中国大陆访客。第一版托管于 GitHub Pages，使用 GitHub Actions 构建并部署；大陆访问体验需要上线实测，架构保持可迁移，不承诺特定地域的访问质量。

第一版不需要数据库、独立后端、站内账号、完整 CMS 或全局状态管理。个人资料管理页在浏览器中调用 GitHub Contents API，使用管理者临时输入的仓库令牌提交资料文件；GitHub Actions 随后重新构建发布。项目和文章仍通过本地 Markdown 更新。

## 2. 技术栈与选型理由

| 技术                    | 职责                                       | 选型理由                                      |
| ----------------------- | ------------------------------------------ | --------------------------------------------- |
| Astro                   | 路由、模板、静态页面、内容集合、图片处理   | 适合内容站点，可避免为整页加载交互框架        |
| TypeScript              | 数据类型与浏览器脚本                       | 降低内容字段和交互代码的维护成本              |
| 原生 CSS                | 全局设计变量、局部组件样式、阅读与打印布局 | 满足定制视觉，不引入额外样式运行时            |
| Markdown + 内容集合     | 项目与博客管理                             | 便于本地写作、Git 审阅与构建校验              |
| Astro Markdown 高亮管线 | 构建时代码高亮                             | 不在浏览器加载完整语法高亮器                  |
| sharp                   | 构建前生成 Open Graph 分享卡 PNG           | 使用本地品牌模板，不依赖在线截图服务          |
| npm                     | 依赖与统一命令                             | 使用常规工具，降低环境配置成本                |
| ESLint + Prettier       | 代码规范、统一格式                         | 使用与 Astro、TypeScript 兼容的配置及格式插件 |
| Vitest                  | 搜索、内容过滤等纯逻辑测试                 | 重点检查有条件组合和边界的逻辑                |
| Playwright              | 构建产物的浏览器测试                       | 验证路由和实际交互，而非仅验证组件内部实现    |
| GitHub Actions          | 检查、构建、部署编排                       | 让质量门槛与部署形成顺序依赖                  |

初始化时选择相互兼容的稳定版本，记录 Node.js LTS 具体版本并统一本地与 CI；提交 package-lock.json，CI 使用 npm ci。不在本文猜测未来安装时的最新版本。

不引入 React/Vue 运行时、整套 UI 库、Tailwind、动画库、搜索引擎服务或状态管理库。后续确有需求时通过单独决策记录评估，不将这些依赖预装为扩展准备。

## 3. 系统架构与模块职责

数据流：仓库内容 → 构建校验与统一查询 → 静态页面及资源 → GitHub Pages → 浏览器局部交互。管理者另可从 `/admin` 提交个人资料 JSON 到仓库，再由同一构建流程发布。

| 模块         | 职责及边界                                                     |
| ------------ | -------------------------------------------------------------- |
| 内容层       | 定义字段、加载内容、校验格式与唯一性；不处理 DOM               |
| 查询层       | 统一公开内容过滤、排序、分类标签汇总、搜索匹配                 |
| 页面层       | 根据路由取内容、组合布局和组件、提供页面元信息                 |
| 组件层       | 可复用展示与局部交互界面，不重复维护个人资料                   |
| 浏览器脚本   | 菜单、复制、搜索、图片弹层、滚动显现和资料编辑，按页面需要加载 |
| 构建与部署层 | 校验、生成、测试、上传及发布记录，不向浏览器暴露凭据           |

网站本身无运行时公共 API；管理页仅向 GitHub API 发起授权读写。搜索所需元信息嵌入博客页面，使用安全序列化，不直接拼接未经转义的内容到脚本。文章正文不进入搜索数据。

关闭或加载失败的 JavaScript 不妨碍阅读主要内容、访问项目文章及邮件链接。搜索、复制和弹层作为增强能力；没有可执行脚本时，文章列表仍完整可见，真实图片可以通过普通链接查看。

## 5. 页面路由与组件设计原则

| 路由             | 数据与主要模块                                                |
| ---------------- | ------------------------------------------------------------- |
| /                | 个人定位、1–2 个精选项目、技能、精选经历、最新 3 篇文章、联系 |
| /projects        | 按作者指定顺序展示项目                                        |
| /projects/{slug} | 构建时枚举项目，生成详情、封面及可选截图和外链                |
| /blog            | 全部已发布文章、搜索框、分类与标签                            |
| /blog/{slug}     | 仅枚举已发布文章，生成正文、目录和元信息                      |
| /about           | 共用个人资料、技能、精选经历和联系信息                        |
| /admin           | 读取并修改 GitHub 中的个人资料、技能和经历；不公开导航入口    |
| 未知路径         | 404 页面及真实 HTTP 404 状态                                  |

内部链接与 canonical 使用统一 URL 生成规则。内容 slug 为稳定的小写英文短名称，可使用数字和连字符，不依赖中文标题自动改变；重复或非法 slug 导致构建失败。逻辑路径沿用 PRD，托管平台的目录索引与尾斜杠归一化在部署核实时统一，不能出现重复 canonical。

BaseLayout 统一文档语言、页头页脚、跳至正文入口和 SEO；ArticleLayout 负责长文宽度、目录和阅读样式。导航当前栏目在构建时按路径判断，详情页归属于对应栏目。

个人信息、联系信息和技能使用同一份数据。项目卡片允许名称和主体进入详情，但独立外链不得嵌套在主链接中。缺失截图、社交或演示地址时省略对应区域或按钮。

第一版采用普通多页面导航。页面进入淡入只作为非阻塞增强，不引入客户端路由或 Astro 客户端导航机制。浏览器脚本按普通页面生命周期初始化。

## 6. 数据结构与内容管理

### 6.1 个人资料、技能与经历

| 数据       | 建议字段                                                                |
| ---------- | ----------------------------------------------------------------------- |
| profile    | name、wordmark、role、headline、intro、availability、email、socialLinks |
| skills     | id、title、description、tools、projectSlugs（可选）                     |
| experience | id、period、organization、role、contribution、order                     |

个人资料、技能和经历统一保存在 `src/data/profile.json`，由 `profile.ts` 以明确类型导出；管理页编辑同一文件，避免维护两份数据。经历按页面顺序展示，period 作为展示文字，避免将“至今”等自然语言强行解析成日期。技能关联项目使用稳定 slug。

### 6.2 项目 Markdown

顶部元信息包含 slug、title、summary、period、role、stack、cover、order；screenshots、githubUrl、demoUrl 为可选字段。截图项包含图片路径、替代文字及说明。

正文固定使用“项目背景 / 我的工作 / 关键难点与方案 / 成果与收获”四个精简小节。首页所需的一句话成果另设 outcome 字段，避免从正文截取不完整句子。封面承担视觉表达，并标记为项目视觉封面。

### 6.3 文章 Markdown

元信息包含 slug、title、summary、publishedAt、category、tags、published；updatedAt 为可选字段。分类只允许一个，标签为去重后的字符串数组。

日期统一使用 YYYY-MM-DD，不隐式转换为访客时区；按日期倒序排列，同日期以 slug 保持稳定顺序。发布由 published 显式控制，第一版不提供定时发布；未来日期不应被误认为已实现自动定时功能。

内容集合在构建时校验必填字段、日期有效性、重复 slug、资源路径及内部引用。updatedAt 不早于 publishedAt。错误提示包含文件路径及字段名，阻止错误内容发布。

### 6.4 草稿与公开范围

- 未允许公开的草稿存放在仓库之外，不进入 Git 历史、构建输入或 CI 产物。
- 已允许公开源码但暂不上网站的文章可以设置 published: false。它的源码仍是公开的，不能作为私密草稿使用。
- 详情路由、首页文章、博客列表、筛选选项、搜索元信息及站点地图统一使用同一个已发布查询入口。
- 正式构建不生成未发布文章的 HTML 或其专属资源，也不复制原始 Markdown。未发布资源不得放入无条件复制的 public 目录。
- 检查生成产物，确认未发布文章的标题、正文及独有资源没有意外进入输出。

### 6.5 更新流程

项目与文章仍采用“本地编辑 → 检查 → 提交 → 发布”。个人资料可在 `/admin` 输入仓库精细权限令牌，加载 `main` 最新 JSON、编辑并提交；GitHub Actions 检查通过后发布。管理页保存成功仅代表 Git 提交成功，不等于部署完成。

项目与文章图片使用 src/assets 下的本地文件并由内容引用；public 仅放需要原样发布的资源。真实截图必须有替代文字，封面图形不能冒充产品截图。示例内容遵循 PRD 的显式标注要求，正式上线前替换或移除。

## 7. 核心功能实现

### 7.1 搜索与筛选

构建时输出已发布文章元信息及完整静态列表。浏览器读取 q、category、tag 三个 URL 查询参数并初始化控件；每个维度至多一个选中值。

关键词去除首尾空白、忽略英文大小写，按完整输入串分别匹配标题、摘要、分类或任一标签。任一字段匹配即可满足关键词条件；关键词、分类和标签之间为 AND 关系。不实现分词、模糊排序或正文检索。

输入或选择后即时更新列表和结果数量，通过 replaceState 同步 URL，避免每次输入都增加历史项；监听浏览器历史变化以恢复状态。文章中的分类与标签链接直接指向对应查询参数。无效分类或标签按未选中处理并归一化 URL，关键词保留。

搜索结果状态使用合适的 aria-live 提示；清除操作恢复全部文章。默认无 JavaScript 时显示全部文章，不展示无法操作的搜索控件。无结果与完全没有文章分别展示 PRD 规定的状态。

### 7.2 Markdown、目录和代码

使用统一 Markdown 渲染管线，构建时完成代码高亮；明确支持表格等 PRD 所需语法。标题文本、锚点和目录来自同一解析结果，避免中文或重复标题出现跳转不一致。

至少两个二级标题才显示目录；目录以二级标题为主。桌面侧栏展示，移动端使用可折叠控件；标题设置 scroll-margin-top，避开置顶页头。

代码复制使用原始代码文本，不包含行号或按钮文字；Clipboard API 失败时提示手动选择复制，不让错误打断阅读。表格及代码块局部横向滚动，页面本身不溢出。

仅渲染仓库内经过审阅的内容，不接受访客提交 HTML；第一版不允许文章任意内嵌脚本或 iframe。安全序列化搜索数据，外链仅使用允许的链接协议。

### 7.3 菜单、图片与联系

移动菜单提供明确的按钮标签、展开状态和焦点恢复；Esc 或选中链接后关闭。无脚本时导航仍可访问。

图片放大采用原生 dialog 加轻量脚本，处理打开、关闭、Esc 和返回触发元素的焦点；不增加轮播或复杂手势库。无脚本时图片链接打开实际图片。

联系入口严格遵循 PRD 的首页及关于页锚点规则。邮箱同时提供 mailto 链接与复制按钮，复制失败仍可看到完整邮箱。

### 7.4 样式与动效

全局 CSS 变量定义颜色、间距、圆角、宽度和层级；组件局部样式负责具体布局，文章与打印样式集中维护。使用 PRD 的 768 px、1024 px 断点，不由各组件自行定义不同断点。

滚动显现通过 IntersectionObserver 实现，仅执行一次。内容默认可见，脚本初始化成功后再启用增强状态，避免动画失效导致内容消失。首屏背景动画不超过 5 秒，移动端关闭背景漂移；prefers-reduced-motion 下禁用位移和氛围动画。

### 7.5 个人资料管理

`/admin` 是普通静态页面，不作为安全边界；只有持有仓库 Contents 写入权限的 GitHub 令牌才能修改资料。页面读取 `src/data/profile.json` 的最新内容及文件 SHA，表单编辑后通过 GitHub Contents API 向 `main` 提交同一文件；SHA 用于冲突检测，冲突时提示重新加载，不做盲目覆盖。GitHub Actions 继续负责检查、构建与发布。

令牌仅由管理者在页面输入，保留于当前页面，不写入 localStorage、sessionStorage、URL、构建产物或日志；关闭页面即失效。管理者应使用仅限本仓库、仅有 Contents 读写权限且短期有效的精细权限令牌。管理页不进入导航和 sitemap，并设置 noindex；这不等于隐藏页面或身份验证。

## 8. 性能、SEO 与基础安全

- 所有核心内容生成静态 HTML，浏览器仅加载本页需要的脚本；不使用远程字体服务或运行时图标 CDN。
- 本地图片在构建时生成适合显示尺寸的资源，设置宽高与响应式尺寸；非首屏图片延迟加载，首屏关键资源避免延迟加载。
- 代码高亮、目录、内容排序在构建时完成；搜索不传输文章全文。
- SEO 组件统一生成标题、描述、canonical、分享标题和图片地址，具体文字由页面内容提供。
- 使用 Astro 官方站点地图集成或其安装时兼容版本生成已发布页面列表，排除 404；robots 按环境生成。
- 默认分享卡片由 `scripts/generate-social-card.mjs` 在构建前使用 sharp 将本地 SVG 模板转换为 1200×630 PNG；不依赖线上截图服务。姓名和页面标题暂不动态绘入卡片，待真实品牌资料补齐后再评估个性化。
- 正式站以 SITE_URL 生成绝对链接；初次验证时指向平台正式域名，绑定个人域名后统一切换并重新构建。
- 预览使用 noindex，并在托管支持时设置 X-Robots-Tag；禁止收录不等于私密访问。预览不提交站点地图给搜索引擎。
- 使用 HTTPS；外链设置适当的 rel 属性。CI 凭据只在 Secrets 中，不能进入 public、客户端环境变量或仓库。管理页使用由本人临时输入、只发送到 GitHub API 的仓库令牌，不持久化于浏览器。
- 草稿保护以不提交公开仓库为主，robots 不能保护草稿或秘密。
- 根据部署平台支持设置内容类型保护、引用来源策略等响应头；如加入 CSP，需验证脚本与样式兼容，不直接套用导致网站失效的策略。

性能以真实页面和网络验证为准，不承诺在未知网络下的加载时间或评分。大陆访问检查覆盖页面、图片和外链；自定义域名本身不保证网络性能改善。

## 9. 开发规范、测试与 Git 策略

### 9.1 本地命令约定

| 命令                 | 用途                                    |
| -------------------- | --------------------------------------- |
| npm run dev          | 本地开发和内容预览                      |
| npm run check        | Astro / TypeScript 检查和内容一致性校验 |
| npm run lint         | ESLint 检查，不自动改写                 |
| npm run format:check | Prettier 格式检查                       |
| npm run format       | 开发者主动格式化                        |
| npm run test         | 单元测试，一次性运行                    |
| npm run build        | 正式静态构建，输出 dist                 |
| npm run preview      | 本地查看构建结果                        |
| npm run test:e2e     | 对构建产物执行浏览器测试                |

命令在后续初始化时实现。CI 检查不得自动改写并提交源文件。跨平台脚本避免依赖仅 Linux 可用的 shell 写法，照顾当前 Windows 开发环境。

### 9.2 测试策略

| 层级         | 核心场景                                                                |
| ------------ | ----------------------------------------------------------------------- |
| 内容检查     | 必填字段、重复地址、日期、无效内部引用、缺失图片、未发布内容过滤        |
| 单元测试     | 搜索组合、稳定排序、个人资料必填字段和外链校验                          |
| 浏览器测试   | 主要访问路径、移动菜单、搜索、复制、图片弹层、404、管理页模拟加载和保存 |
| 构建产物检查 | 草稿正文及专属资源未输出，站点地图与 canonical 正确，必要页面已生成     |
| 上线人工验收 | PRD 规定的视口、200% 缩放、键盘、减少动态、打印、真实网络和真实设备     |

日常 CI 的浏览器测试以 Chromium 为主，使用 Playwright 管理的浏览器版本；正式上线前补做 Firefox、WebKit 及可用的真实 Safari 验证。WebKit 自动测试不等同于真实 Safari 设备验收，报告应区分覆盖范围。

测试夹具使用明确的虚构测试数据，放在内容集合之外。对可剪贴板失败等场景可使用受控测试替身，保留至少一次真实浏览器走查。不为静态文案逐条编写测试，不默认引入大范围截图回归。

构建预览服务器与线上托管的 404、重定向、缓存可能不同，上线后必须做一次真实 HTTP 状态及静态资源检查。

### 9.3 Git 约定

- main 为正式发布分支，短期分支通过 PR 合并；个人项目不强制增加第二位人工审阅者。
- 提交信息简洁说明意图，可使用 feat、fix、docs、content、chore 前缀。
- 提交源码、内容、配置和依赖锁文件；忽略依赖目录、dist、测试产物、真实环境变量及本地临时文件。
- 尽可能配置 main 的必需状态检查。部署流程本身仍验证检查结果，不仅依赖分支保护设置。
- 重大依赖升级单独开分支；定期小步升级，避免同时改变框架、内容格式与部署平台。

## 10. 构建、部署与维护

### 10.1 发布编排

GitHub Actions 作为唯一发布入口，顺序执行：安装锁定依赖 → 类型、内容、规范与格式检查 → 单元测试 → 构建 → 构建产物与浏览器测试 → 上传该次已经测试的 dist。

GitHub Pages 使用 GitHub Actions 作为唯一发布入口，避免平台分支构建绕过本工作流的发布门槛。

| 事件               | 行为                                 |
| ------------------ | ------------------------------------ |
| 同仓库短期分支更新 | 检查通过后发布对应分支预览，回传链接 |
| main 更新          | 检查通过后发布正式环境               |
| 外部 fork PR       | 只运行不带部署凭据的检查，不自动部署 |
| 任意检查失败       | 停止后续部署，保留线上现有版本       |

部署作业按目标环境串行化；正式部署前确认提交仍是应发布的 main 版本，跳过过期运行。不要在未结束的上传中盲目取消以制造不确定状态。同一提交的重复事件应避免重复发布。

仅受信任的仓库分支可进入带凭据的部署作业；外部 PR 不使用能暴露 Secrets 的执行方式。Token 采用最小必要权限，部署过程不输出凭据。

### 10.2 配置与环境变量

| 配置              | 性质与用途                                          |
| ----------------- | --------------------------------------------------- |
| SITE_URL          | 公开配置，当前正式站的绝对 URL，用于 SEO 与站点地图 |
| DEPLOY_CONTEXT    | production / preview / local，控制收录与环境行为    |
| GITHUB_REPOSITORY | Actions 默认提供，用于推导 Pages 项目路径           |
| SITE_URL          | 可选仓库变量；默认推导为 https://{owner}.github.io  |
| GITHUB_PAGES_BASE | 可选仓库变量；默认从仓库名推导子路径                |

构建和访客页面不需要秘密。资料管理令牌由管理者在浏览器中临时输入，不配置为构建环境变量。需要公开给浏览器的配置必须明确审核，不能通过复制整个环境对象传入。环境示例只包含变量名及说明。

### 10.3 GitHub Pages 配置与发布

- 仓库 Settings → Pages 将 Build and deployment source 设为 GitHub Actions。
- `deploy-pages.yml` 只在 `main` 更新或手动触发时运行；部署前必须通过类型/内容检查、Lint、格式检查、单元测试、浏览器测试和静态构建。
- 当前演示资料可发布，页面继续显式标注示例。`npm run check:release` 保留供将来正式内容验收使用，但不再阻断现阶段的 GitHub Pages 部署。
- Astro 构建依据 `GITHUB_REPOSITORY` 自动推导站点域名及仓库子路径；组织根站点 `{owner}.github.io` 使用 `/`，普通项目仓库使用 `/{repo}/`。自定义域名后通过仓库变量 `SITE_URL` 覆盖绝对站点地址。
- 路由链接、favicon、分享图、canonical 和 sitemap 均需遵循部署 base path；本地开发使用根路径。
- GitHub Pages 返回真实 404 页面；上线检查详情刷新、资源路径、查询参数、HTTPS 与搜索元信息。

### 10.4 上线和回退

先在 GitHub Pages 域名验证页面、资源、404 和交互，再测试大陆不同网络的实际访问。绑定自定义域名后更新 SITE_URL，重新构建并检查 canonical、分享图及站点地图。

保留发布所对应的 Git 提交和成功构建记录。需要回退时，将已验证历史版本通过受控工作流重新发布，仍通过检查门槛；不依赖未经核实的平台“一键回滚”。失败部署不应主动清空线上内容。

新站点迁移或旧域名替换时核实重定向支持，保留文章和项目的稳定路径。站点资源自托管，便于将相同静态产物迁移到其他平台。

## 11. 技术难点与后续扩展

| 难点               | 处理原则                                         |
| ------------------ | ------------------------------------------------ |
| 公开仓库与草稿隐私 | 私密草稿不进入仓库；published 字段仅控制网站发布 |
| 静态托管路由差异   | 在真实部署环境检查详情刷新、尾斜杠与 HTTP 404    |
| 搜索与浏览器历史   | URL 为可分享状态来源，初始化和历史恢复走同一逻辑 |
| 中文与重复标题目录 | 使用同一渲染管线生成标题 ID 与目录               |
| 弹层与移动端无障碍 | 原生控件配合焦点管理，键盘和触摸均需走查         |
| 动效与可读性       | 内容默认可见，减少动态与移动端降级优先           |
| 发布竞态           | CI 单一部署入口、环境串行、过期提交跳过          |
| 大陆访问体验       | 真实网络验证；平台与域名选择不替代实测           |

后续可按 PRD 增加项目筛选、文章分页、RSS、英文版、全文搜索或 PDF 简历。先评估静态构建能否继续满足，再考虑新增服务。MDX 仅在明确需要文章交互组件时引入；CMS、数据库、评论及身份系统均需单独产品与架构决策。

任何扩展不得改变既有内容 URL、删除既定功能或悄然放宽草稿公开规则。技术设计变更需更新本文并说明原因。
